# Benchmarks

Performance tests for library components. Benchmarks are built separately and are never part of `main.cpp`.

## How a benchmark comes to be

The scenario is designed by the repository owner, per structure — which operations, in what mix, in what access pattern. What gets written here is that scenario turned into one concrete, fully deterministic test.

## Rules

- **Deterministic.** Same binary, same input, same work — every run. No `rng`, no `chrono` seeding, no time-dependent branching inside the measured region. Test data is generated by a fixed-seed LCG or an explicit closed-form formula written into the benchmark itself.
- **Sizes.** `n = 2e5` for structures whose operations are O(log n) (so O(n log n) total). Other complexity classes get a size chosen to land in the same time band, stated in the benchmark file.
- **Measure the structure, not the I/O.** Input is generated in-process; only the operation loop is timed, using `chrono::steady_clock`.
- **Consume the results.** Accumulate query answers into a checksum and print it, so the optimizer cannot delete the work being measured. The checksum doubles as a correctness signal across implementations.
- **Warm-up.** One untimed pass over a smaller instance before the measured region.
- **One structure per benchmark file**, named `<component>.cpp`.
